# Decisions log

One line each: ID · date · decision — reason.

- D-01 · 2026-10-18 · Greenfield: repository was empty, so the v2 stack is adopted as-is — no existing code to preserve.
- D-02 · 2026-10-18 · Modular monolith in a pnpm monorepo (web, api, domain, contracts, i18n) — one team, strong consistency needs, simplest deploy.
- D-03 · 2026-10-18 · All business rules live in `packages/domain` as pure functions returning `Result` — testable without DB, reproducible snapshots.
- D-04 · 2026-10-18 · Prisma **7.x stable** pinned (not 8.0 RC, which is currently npm `latest`): connection URL in `prisma.config.ts`, `prisma-client` generator, `@prisma/adapter-pg` at runtime — avoid pre-release ORM in a product handling money.
- D-05 · 2026-10-18 · Draft schema validated with Prisma's WASM validator (7.1 and 8.1) in Phase 1; superseded by D-33 (schema now lives in apps/api).
- D-06 · 2026-10-18 · UUIDv7 primary keys — time-sortable, non-guessable, safe in URLs.
- D-07 · 2026-10-18 · Scores stored as integer hundredths (0–10000) instead of `Decimal(5,2)` — identical precision, exact integer math in TS and SQL, no decimal library.
- D-08 · 2026-10-18 · Weights in basis points, must sum to exactly 10000 — integer validation, no float tolerance.
- D-09 · 2026-10-18 · Money as `BigInt` whole UZS, transported as JSON strings — avoids JS number precision issues.
- D-10 · 2026-10-18 · Rounding: once per stored number, half-up; reward amounts rounded down to step — never exceed budget/cap.
- D-11 · 2026-10-18 · One `Assessment` table for CANDIDATE / PERFORMANCE / LEVEL_REVIEW with a CHECK on subject columns — one scoring engine, one review UI.
- D-12 · 2026-10-18 · Promotion eligibility uses LEVEL_REVIEW assessments; monthly performance is context only — keeps "level" and "monthly result" separate as required.
- D-13 · 2026-10-18 · Level requirements cumulative up to target level; failed checks never lower a current level.
- D-14 · 2026-10-18 · Learning and mentoring modelled as evidence types, not separate tables — same lifecycle (submit, verify, allocate).
- D-15 · 2026-10-18 · `EvidenceAllocation` unique (evidenceId, periodId) enforces "count once" at DB level — for CONTRIBUTION evidence (see D-27).
- D-16 · 2026-10-18 · `governmentFee` is not a selectable measure field in metric configs — revenue misuse impossible by construction.
- D-17 · 2026-10-18 · Ranking = competition ranking (1,2,2,4), cohort = specialty + rubric version + period, min cohort 3.
- D-18 · 2026-10-18 · Reward pool per policy, policy bound to specialty + rubric version — no cross-specialty comparisons; capped remainder not redistributed by default (flag).
- D-19 · 2026-10-18 · Salary point = position inside band by progress between current and next level threshold, range ± 10 % of band width — explainable, uses only configured data.
- D-20 · 2026-10-18 · Server-side sessions in Postgres + CSRF synchronizer token; Next.js rewrites `/api/*` to Fastify for same-origin cookies.
- D-21 · 2026-10-18 · Permission + scope (OWN / ORG_UNIT / ORG) model; org-unit subtree via materialized path.
- D-22 · 2026-10-18 · Separation of duties on by default (no self-verification/approval, approver ≠ recommender).
- D-23 · 2026-10-18 · Localized configuration text stored as JSON `{uz, ru, en}` with `uz` required; user content never translated.
- D-24 · 2026-10-18 · Background jobs on a Postgres table with `SKIP LOCKED` — no Redis needed for MVP volume.
- D-25 · 2026-10-18 · AI provider defaults to Mock until legal answers Q20; pseudonyms + PII scrubber on every AI input.
- D-26 · 2026-10-18 · Audit table append-only via DB privileges; separate migrator and app DB roles.
- D-27 · 2026-10-18 · Evidence split into RECORD (SERVICE_RECORD, SALE, CUSTOMER_FEEDBACK) and CONTRIBUTION (all others). One service record legitimately feeds quality (errorFree) and volume (tier); double counting is prevented by forbidding two criteria from reading the same type.field, while contributions are allocated to exactly one criterion per period. Found while implementing EX1 — the Phase 1 rule "one evidence → one criterion" contradicted EX1.
- D-28 · 2026-10-18 · TypeScript pinned to 6.0.x: TS 7.0 (npm latest) is not yet supported by typescript-eslint (peer < 6.1).
- D-29 · 2026-10-18 · ESLint enforces domain purity: no Node I/O, framework or app imports, no Math.round/floor/ceil or parseFloat in packages/domain.
- D-30 · 2026-10-18 · Coverage threshold 100 % (lines, branches, functions) on packages/domain; impossible branches are removed by restructuring, not suppressed.
- D-31 · 2026-10-18 · Level requirements: gate = blocks; non-gate = advisory shortfall shown to the approver. Promotion blockers: minApprovedAssessments (default 1) and minMonthsAtPrevious (default 0).
- D-32 · 2026-10-18 · Full local check is `pnpm run verify` (lint, format, typecheck, tests + coverage); `pnpm ci` is a reserved pnpm command.
- D-33 · 2026-10-18 · Migration fallback without native engine binaries: Prisma's schema engine as WASM (exact CLI engine build) creates migrations schema-to-schema (snapshot stored per migration); deploy runs each migration in one pg transaction with Prisma-compatible `_prisma_migrations` rows. Found: the CLI with a missing binary can exit 0 with an empty diff, and the engine's adapter path splits plpgsql `$$` bodies and applies migrations partially — both avoided.
- D-34 · 2026-10-18 · All event timestamps `timestamptz(3)` (Prisma default is timestamp without time zone).
- D-35 · 2026-10-18 · Audit append-only enforced by triggers (UPDATE/DELETE/TRUNCATE) for every role, not only by revoking privileges from the app role — also binds the owner.
- D-36 · 2026-10-18 · Rubric version locks itself in the DB when the first assessment references it (AFTER INSERT trigger) — the lock cannot be forgotten by application code.
- D-37 · 2026-10-18 · CHECK expressions that can be NULL are wrapped in `IS TRUE` (NULL passes a CHECK).
- D-38 · 2026-10-18 · `pnpm run verify` includes DB tests (`test:db`), which drop and recreate only a database whose name contains "test".
- D-39 · 2026-10-19 · Env parsing: single `loadConfig()` returns a Zod-validated `Config` or throws listing every failing key — fail-fast at boot, no partial-config bugs, zero reads of `process.env` elsewhere.
- D-40 · 2026-10-19 · `X-Request-Id`: adopt the inbound header only when it matches `/^[\x20-\x7E]{1,128}$/`, otherwise mint UUID v4. Keeps logs correlatable across proxies but refuses control chars and giant strings that would poison log lines or GC.
- D-41 · 2026-10-19 · Error contract: every API error is RFC 9457 `application/problem+json` with a stable `code: orbita:<category>:<name>` (also the i18n key) and the request id in `instance`; 500 never carries `detail` so internal messages never reach the client.
- D-42 · 2026-10-19 · `buildApp()` is a pure factory — tests inject a `PrismaClient` and `app.inject()`, production calls `app.listen()`. No module may read `process.env` after `server.ts`.
- D-43 · 2026-10-19 · Session cookie stores a 32-byte random token; the DB keeps only its SHA-256 and a separate CSRF value. A DB snapshot never leaks a live cookie; lookup still works because the server hashes the cookie's token before querying by `tokenHash`.
- D-44 · 2026-10-19 · Rate limits in process memory (sliding window): login 5/min per IP+email, reset 3/hour per email, cleared on successful login. Sufficient for a single-box MVP; Redis/Fail2Ban come with multi-node deploy.
- D-45 · 2026-10-19 · Argon2id via `@node-rs/argon2` (prebuilt binaries, no node-gyp). Parameters m=19 MiB, t=2, p=1 (OWASP 2024 interactive baseline); encoded in the hash so parameter bumps re-hash lazily on next successful login.
- D-46 · 2026-10-19 · Unknown-email and wrong-password paths return the same `orbita:auth:invalid_credentials` and burn an Argon2 verify against a cached dummy hash so timing is indistinguishable.
- D-47 · 2026-10-19 · Password reset: single-use token (SHA-256-stored, 30 min TTL), identical API reply whether email exists or not, confirm revokes every session for the user — a thief who held a cookie at reset time loses access.
- D-48 · 2026-10-19 · Authorization is a function-returning factory on `app.requirePermission`: each preHandler reads the session cookie, loads the actor once, caches on `req.actor`. Second preHandler on the same route reuses the cache without a DB round-trip. Request-decorated functions were avoided because Fastify 5 does not bind `this` to request instances for decorated function values.
- D-49 · 2026-10-19 · AuditEvent writer takes a `Prisma.TransactionClient`, never a bare client — audit rows commit (or roll back) atomically with the business change. The writer exposes no update/delete API because the append-only trigger (D-35) refuses them at the DB level.
- D-50 · 2026-10-19 · Web ↔ API: Next's dev/prod proxy rewrites `/api/v1/*` to the Fastify origin, so the session cookie is first-party. `apiFetch` throws a typed `ApiError` with the problem+json `code` + `status`; the UI maps codes to i18n keys (login invalid/locked/rate_limited), never raw server strings.
